## Findings
- [note] .cargo/config.toml:5, scripts/sherpa-onnx.mjs:62-196 — Deviation from the stack decision: the build uses `SHERPA_ONNX_LIB_DIR` instead of `SHERPA_ONNX_ARCHIVE_DIR`. I consider it security-equivalent or stronger. sherpa-onnx-sys build.rs (v2.0.1, l.115-126) uses LIB_DIR only, and it fails if the folder is missing, so `download_prebuilt_libs` (ureq) never runs. The libraries come only from an archive that matched the committed SHA-256 (`fetch` checks the `.part` download before rename and again with `verify`). The human gate still has to accept it, as build.md says.
- [note] scripts/sherpa-onnx.mjs:150-157 — `verifyLibs` checks only the `lib/SOURCE` marker, not the contents of the unpacked or objcopy-rewritten `.a` files. Someone with write access to `src-tauri/native/lib/` on a dev machine could swap libraries without anyone noticing. CI always unpacks fresh, and the risk is local only. A later hardening could also record SHA-256s of the derived libs in SOURCE.
- [note] .github/workflows/ci.yml:58 — `actions/cache@v4` is pinned by tag, not by commit SHA. This matches the existing steps (checkout, setup-node, rust-cache). It adds no new gap, but the cached archive is re-verified by `fetch`, so a poisoned cache cannot get past the pin.
- [note] src-tauri/src/engines/models.rs:476-500 — The ONNX top-level parser is bounded: 4096 fields, 64 KiB per metadata entry, a length check against the file size before every skip or read, and a cap of 10 varint bytes. In theory a crafted file in a scanned folder could make it allocate up to 4096 × 64 KiB, but the folders are local and owned by the user. No action needed.
- [note] src-tauri/src/recording/mod.rs:430-436, 489-493 — Embeddings and centroids are dropped on stop and on drop of the Recorder, but not zeroized. That is acceptable for in-memory personal data under the current NFRs. Voice profiles, which are out of scope here, should get explicit zeroize.
