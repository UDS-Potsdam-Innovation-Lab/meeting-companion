## Findings
- [note] src-tauri/src/phone_view/server.rs:573 — the 32-connection cap is global, not per address. One device on the LAN can hold all 32 slots by sending slow headers (each lasts up to 10 s, then reconnects). Rate limiting only counts finished requests, so the view is blocked for real phones while this goes on. The spec asks for exactly this global cap and the impact is denial of service on a short-lived opt-in view, so it does not block. A per-address connection cap (for example 8) would be a cheap fix for 010 or a follow-up.
- [note] src-tauri/src/phone_view/mod.rs:276 — the token goes over plain HTTP, so anyone sniffing the same Wi-Fi can capture it from the bearer header. The human accepted this on 2026-10-31 (010-voice-profiles/stack-decision.md, spec "out: TLS"). Consumers that add routes returning or changing personal data (010 consent) should keep that exposure in mind.
- [note] src-tauri/src/phone_view/mod.rs:351-356 — pausing keeps the view open. This matches the spec (it closes when recording stops, not on pause) and is documented in build.md.
- [note] src-tauri/src/phone_view/http.rs:124-133 — `ConsumerRoutes::get` relies on the comment "must not change anything". A GET with no `Origin` header passes the CSRF check. The bearer token still guards it, so this is not exploitable now. 010 should keep every change behind `post`.
- [note] `cargo audit` / `npm audit` are not configured for this project. `if-addrs` 0.15 (MIT/BSD, maintained) is the only new crate outside the existing lock tree. `rqrr` is a dev-dependency only. Versions are pinned through Cargo.lock.
